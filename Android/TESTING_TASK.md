# Задание: тесты на логику Android-приложения

Документ самодостаточный — читать историю переписки не нужно.

## 1. Что за проект

Контроллер помпы для 19-литровой бутыли с водой. Две части в одном
репозитории:

| Папка | Что |
|---|---|
| `CH582F_MotorBLE` | прошивка, чип CH582F, BLE |
| `Android` | приложение для настройки и наблюдения |

Протокол описан в [`CH582F_MotorBLE/ANDROID_APP_TASK.md`](../CH582F_MotorBLE/ANDROID_APP_TASK.md).
Коротко: команды пишутся в характеристику `0xFFE1` тремя байтами, ответы
приходят уведомлениями на `0xFFE2`. Три типа ответов — телеметрия, значение
параметра, квитанция.

## 2. Что уже есть и чего нет

Тесты: `app/src/test/java/com/example/ch582motor/ProtoTest.kt`, 13 штук.
Все проверяют разбор и сборку пакетов плюс сверку таблицы параметров
с прошивкой. Это самая простая часть кода, и она покрыта.

**Не покрыто ничего из того, где живут настоящие ошибки** — вся логика
`MotorViewModel`.

За время разработки в этом файле нашлись три бага, и все три поймались
глазами при чтении, а не тестами:

1. **`catch (e: Exception)` ловил `CancellationException`.** Отмена
   подключения показывалась пользователю как ошибка «Job was cancelled».
2. **Порядок очереди ожиданий.** Квитанция в протоколе не говорит, на что
   она — байт `code` это либо id параметра, либо код команды. Различаются
   они только позицией в очереди `expectations`. Ожидание клалось *после*
   отправки, то есть квитанция могла прийти раньше, чем её начали ждать.
3. **Флаг `dirty` расходился с фактом.** Он взводился на успешной записи
   и не умел «развзводиться», если значение вернули к прежнему вручную.
   Заменён на сравнение со снимком `saved`.

Такие ошибки — ровно то, что ловится юнит-тестами дёшево и надёжно.

## 3. Препятствие: тестировать нечего

`MotorViewModel` нельзя запустить на JVM. Он тянет за собой Android
тремя нитями:

```kotlin
class MotorViewModel(app: Application) : AndroidViewModel(app) {
    private val manager = MotorBleManager(app)      // BLE, Nordic
    private val presetStore = PresetStore(app)      // SharedPreferences
    fun bluetoothEnabled(): Boolean { ... }         // BluetoothManager
```

Плюс `startScan()` дёргает `MotorScanner.scan()` — object, который сразу
лезет в системный сканер.

**Robolectric не брать.** Он медленный, тянет полбоку Android и лечит
симптом. Задача в том, чтобы логика не зависела от платформы вовсе.

## 4. Что сделать: шов между логикой и BLE

### 4.1 Интерфейс

Завести интерфейс, скажем `BleLink`, и спрятать за ним всё платформенное.
Поверхность снимается с текущих обращений к `manager` в `MotorViewModel`:

```kotlin
interface BleLink {
    val packets: Flow<Packet>
    val connection: StateFlow<ConnectionPhase>

    var sleepRequested: Boolean

    fun bluetoothEnabled(): Boolean
    fun scan(): Flow<List<FoundDevice>>

    suspend fun connectTo(address: String)
    suspend fun disconnectFrom()
    suspend fun abortConnect()

    suspend fun sendCommand(code: Int)
    suspend fun sendSetParam(id: Int, value: Int)
    suspend fun sendGetParam(id: Int)

    fun close()
}
```

**Обратите внимание на `connectTo`.** Сейчас метод принимает
`BluetoothDevice`, а этот класс в юнит-тесте не создать. Поэтому в интерфейсе
он должен принимать **адрес строкой**, а реализация пусть достаёт устройство
через `BluetoothAdapter.getRemoteDevice(address)`. Заодно из `FoundDevice`
уйдёт поле `device`, и структура станет чистыми данными, пригодными для
тестов.

Реализация `BleLinkImpl(context)` оборачивает существующие
`MotorBleManager` и `MotorScanner` — их переписывать не надо.

### 4.2 Хранилище пресетов

Так же: интерфейс `PresetStorage` с методами `load()` / `save(list)`,
реализация на `SharedPreferences` уже написана в `PresetStore`.
Для тестов — список в памяти.

### 4.3 ViewModel

```kotlin
class MotorViewModel(
    private val ble: BleLink,
    private val presetStore: PresetStorage,
) : ViewModel()
```

`AndroidViewModel` больше не нужен. Compose получает экземпляр через
фабрику: `viewModel(factory = MotorViewModel.factory(LocalContext.current))`.

### 4.4 Диспетчер

`viewModelScope` работает на `Dispatchers.Main`, которого на JVM нет.
В тестах подменяется через `Dispatchers.setMain(StandardTestDispatcher())`
из `kotlinx-coroutines-test` — зависимость **уже подключена**
(`app/build.gradle.kts`, `testImplementation(libs.kotlinx.coroutines.test)`).

`StandardTestDispatcher` даёт управление временем: `advanceTimeBy()` нужен
для проверки дебаунса и таймаутов, они там по сотням миллисекунд.

## 5. Что покрыть

Список отсортирован по ценности. Первые пять — это ровно те места, где
уже были ошибки.

### Квитанции и очередь ожиданий

1. Две записи параметров подряд → две квитанции → каждая применилась
   к своему id, значения не перепутались.
2. Квитанция с `status = 1` откатывает `edited` к прежнему значению
   и не трогает соседний параметр.
3. Квитанция на команду и квитанция на параметр с одинаковым байтом `code`
   различаются по позиции в очереди. Записать параметр 2, затем послать
   `SAVE` (код 2) — обе квитанции должны разойтись по назначению.
4. Ожидание кладётся **до** отправки: подключение ставит `TELEMETRY_ON`
   в очередь раньше, чем зовёт `sendCommand`. Фейк, отвечающий квитанцией
   синхронно внутри `sendCommand`, поймает регрессию.
5. Квитанция без ожидания в очереди игнорируется и ничего не ломает.

### Отмена и ошибки

6. `cancelConnect()` не порождает сообщение об ошибке и зовёт
   `abortConnect()`.
7. Отказ `MOTOR_START` даёт текст про отсечку по разряду, а не общий
   «команда отвергнута». Отказ `SAVE` — текст про остановку помпы.
8. `SLEEP` взводит `sleepRequested` до отправки и снимает его, если
   отправка бросила исключение.

### Расхождения с flash

9. После `loadAllParams()` список `changes` пуст.
10. Запись параметра создаёт ровно одно расхождение с верными `from` и `to`.
11. Успешная квитанция `SAVE` очищает список.
12. Возврат значения к прежнему **убирает** расхождение — это регрессия
    на старый флаг `dirty`, который так не умел.

### Чтение параметров

13. `loadAllParams()` шлёт 13 запросов `sendGetParam` по одному, а не пачкой.
14. Молчание на запрос → повтор, три попытки, потом параметр попадает
    в сообщение «не прочитаны».
15. Подписка на ответ открывается раньше отправки запроса — иначе ответ,
    пришедший синхронно, будет потерян. Фейк отвечает внутри `sendGetParam`.

### Дебаунс и запись

16. Несколько `editParam` подряд по одному id → одна запись через 400 мс
    с последним значением.
17. `applyParam` пишет немедленно и отменяет отложенную запись.
18. Запись значения, равного текущему, не шлётся вовсе.

### Прочее

19. Разрыв связи чистит `telemetry`, `pending`, `saved`, но оставляет
    `params` — форма не должна опустеть.
20. После записи `PWM_MIN` или `PWM_MAX` идёт перечитывание обоих:
    прошивка меняет их местами, если перепутать.
21. `PresetStore`: сохранение и чтение туда-обратно, перезапись
    одноимённого, пропуск параметра с id, которого больше нет в таблице.

## 7. Ограничения

- **Новых зависимостей не добавлять**, кроме тестовых. `kotlinx-coroutines-test`
  уже есть и достаточен. Turbine удобнее для потоков, но не обязателен —
  решать по ходу.
- **Robolectric не брать**, см. раздел 3.
- `ProtoTest.kt` не трогать, он про другое и работает.
- Поведение приложения меняться не должно: это рефакторинг ради
  тестируемости плюс тесты. Любое изменение логики — отдельно и осознанно.
- Комментарии в проекте объясняют **почему**, а не что. Держаться этого же
  стиля.
