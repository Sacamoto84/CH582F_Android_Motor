# Незакрытые проблемы: ISP, отладчик, самопроизвольные сбросы

Документ для отдельной сессии. Самодостаточный — читать историю переписки
не нужно.

Статус: **A обойдена, B не решена, C обойдена но не объяснена.** Ниже что
выяснено достоверно, что уже пробовали, и что делать дальше.

---

## 1. Постановка

Плата **WeAct CH57x/CH58x Core Board V1.0** с **CH582F**, питание —
**постоянно подключённый аккумулятор 1S Li-ion**, выключателя питания нет.
Прошивка — контроллер помпы, описание в [README.md](README.md).

Три беды:

**A. Не попасть в ISP-загрузчик.** Перепрошить устройство нечем, если
отладчик не работает.

**B. Отладчик WCH-Link работает крайне плохо** — «тупо не видит чип».
Иногда прошивает, после чего перестаёт видеть.

**C. Самопроизвольные сбросы `RPOR` при частых пусках мотора.** Разбор
в разделе 7: питание ни при чём, объяснения нет, обойдено выключением
DC-DC и автосна стека.

## 2. Что выяснено достоверно

### 2.1 Из софта можно сделать сброс типа «подача питания» (RPOR)

**Это опровергает прежний вывод этого документа.** Раньше здесь было
написано «программным сбросом в ISP попасть нельзя» на основании
комментария в `StdPeriphDriver/inc/CH583SFR.h`:

```c
#define R8_GLOB_CFG_INFO  (*((PUINT8V)0x40001045))  // RO
#define  RB_BOOT_LOADER   0x20   // 0 = application status (by software reset),
                                 // 1 = boot loader status
```

Комментарий описывает **голый** `RB_SOFTWARE_RESET`. Но в самом SDK WCH
лежит последовательность, дающая сброс другого типа:

```c
FLASH_ROM_SW_RESET();
sys_safe_access_enable();
R16_INT32K_TUNE = 0xFFFF;          /* <- вот это и есть ключ */
sys_safe_access_disable();
sys_safe_access_enable();
R8_RST_WDOG_CTRL |= RB_SOFTWARE_RESET;
sys_safe_access_disable();
while(1);
```

Она встречается в SDK трижды, и в одном месте прямо подписана:

| Файл | Функция | Комментарий WCH |
|---|---|---|
| `StdPeriphDriver/CH58x_sys.c:293` | `HardFault_Handler()` | 硬件错误中断，进入后执行复位，**复位类型为上电复位** — «тип сброса **power-on**» |
| `StdPeriphDriver/CH58x_flash.c:153` | `UserOptionByte_Active()` | 用户配置字生效函数 — применение байтов конфигурации |
| `StdPeriphDriver/CH58x_pwr.c:393` | выход из Shutdown | — |

Второй пункт независимо подтверждает суть: байты конфигурации
перезащёлкиваются **только при подаче питания**. Раз этой
последовательностью WCH их применяет, значит она даёт именно RPOR.

Следствие: ПЗУ-загрузчик после неё отрабатывает штатно и **опрашивает
PB22**. То есть удержание кнопки BOOT + такой сброс = вход в ISP,
без всякого стирания флеша.

Про OTA: в `Datasheet/BLE/WCH蓝牙空中升级（BLE OTA）.PDF` их собственный OTA
использует «软复位进入IAP程序» — программный сброс в свой IAP
в пользовательском флеше. Это другая задача, к ПЗУ-загрузчику отношения
не имеет.

### 2.1.1 Как проверить, не рискуя ничем

`APP/main.c:196` уже печатает причину сброса. После нового кода
удержание кнопки должно дать в UART:

```
reset: POR
```

вместо прежнего `reset: SW`. Если печатает `POR` — механизм работает,
и дальше вопрос только в том, доедет ли до ПЗУ удержанный PB22.
Никакого ISP для этой проверки не нужно.

### 2.2 Типы сброса

`R8_RESET_STATUS & RB_RESET_FLAG`, адрес `0x40001044`:

| Код | Имя | Что это |
|---|---|---|
| 000 | SR | программный, `RB_SOFTWARE_RESET` |
| 001 | RPOR | настоящая подача питания **или срабатывание LVR** |
| 010 | WTR | сторожевой таймер |
| 011 | MR | внешний сброс по выводу RST# |
| 101 | GRWSM | пробуждение из Shutdown |

Прошивка печатает это в UART при старте строкой `reset: ...`.

### 2.3 Кнопка RST на плате мертва с завода

Даташит `CH583DS1_en.PDF`, таблица 2-3 «Description of user non-volatile
configuration information»:

| Бит | Имя | Значение по умолчанию |
|---|---|---|
| 3 | `CFG_RESET_EN` | **0** — вывод RST# выключен |
| 4 | `CFG_DEBUG_EN` | 1 — SWD включён |
| 6 | `CFG_BOOT_EN` | 1 — загрузчик разрешён |

**Это и есть корень проблемы A.** Кнопка K1 на плате подписана «RST», но
пока `CFG_RESET_EN = 0`, PB23 остаётся обычным GPIO. Внешний сброс сделать
нечем, питание не передёрнуть — тупик.

### 2.4 Распиновка кнопок

| Кнопка | Пин | Роль |
|---|---|---|
| K1 «RST» | PB23 | вывод сброса RST#, **выключен по умолчанию** |
| K2 «BOOT» | PB22 | пин ISP-загрузчика **и** пользовательская кнопка прошивки |

`BOOT_PIN` можно перенести на PB11 через опцию (бит 9 конфигурационного
слова, константа `BOOT_PIN_PB22` в `StdPeriphDriver/CH58x_flash.c`).

## 4. Что делать дальше — по порядку

### Шаг 0. Проверить RPOR-сброс. Кода уже написан, риска ноль

Собрать, прошить, зажать кнопку на 5 с и держать до конца мелодии.
Смотреть UART:

1. **Печатает `reset: POR`?** Механизм из п. 2.1 работает. Если нет —
   печатает `SW` — значит `R16_INT32K_TUNE` на CH582F так не действует,
   и дальше только шаг 1.
2. Печатает `POR`, но кнопку **не отпускать** — увидит ли WCHISPTool
   устройство?
   - Да → проблема A решена, ничего больше не нужно.
   - Нет → ПЗУ до PB22 не доходит либо линия ISP не разведена (см. п. 5,
     USB может быть только питанием). Идти в шаг 1.

Ничего не стирается, откатывать нечего.

### Шаг 1. Включить вывод сброса. Это решает проблему A целиком

В **WCH-LinkUtility** открыть настройки байтов конфигурации чипа и
поставить галку разрешения вывода сброса (`CFG_RESET_EN`). После этого
работает штатная процедура входа в ISP:

> зажать K2 (BOOT) → нажать и отпустить K1 (RST) → отпустить K2

Никакого кода, питание передёргивать не надо.

**Из прошивки то же самое умеет `UserOptionByteConfig()`** в
`StdPeriphDriver/CH58x_flash.c`:

```c
UserOptionByteConfig(ENABLE,   /* RESET_EN — включить RST# */
                     ENABLE,   /* BOOT_PIN — оставить на PB22 */
                     DISABLE,  /* UART_NO_KEY_EN */
                     0);       /* защита флеша */
```

⚠️ **Осторожно.** Комментарий WCH к этой функции: после её вызова
двухпроводной отладочный интерфейс по умолчанию **выключается**, и нужен
их специальный `.S`-файл. При нерешённой проблеме B это способ остаться
совсем без доступа к чипу. **Сначала утилитой, код — только если утилита
почему-то не может.**

### Шаг 2. Крайняя мера: стереть начало флеша и уйти в RPOR

Работает без опроса PB22 вообще: ПЗУ видит пустое приложение и остаётся
в ISP само, с таймаутом ожидания. Тот же `reboot_as_power_on()`, но перед
ним стирание нулевого блока:

```c
__HIGH_CODE
static void erase_and_reboot_to_isp(void)
{
    while(FLASH_ROM_ERASE(0, EEPROM_BLOCK_SIZE))
    {
        ;   /* ждём успешного стирания первых 4 КБ */
    }
    reboot_as_power_on();
}
```

`EEPROM_BLOCK_SIZE` = 4096, `FLASH_ROM_ERASE` — оба из
`StdPeriphDriver/inc/ISP583.h`.

🔴 **Односторонний билет.** После стирания приложения нет. Если ISP
не отзовётся — а он может не отозваться, потому что D+/D− на плате,
возможно, не разведены (п. 5), а UART1 занят отладочным выводом — чип
остаётся доступен только через WCH-Link, то есть через нерешённую
проблему B.

**Порядок такой: сначала шаг 0, потом шаг 1, и только если оба
не сработали — этот.** В код намеренно не добавлено.

### Шаг 3. Разбираться с отладчиком

`DEBUG_FRIENDLY` показал, что дело не в прошивке. Проверять железо и
инструмент:

- **Режим WCH-Link.** Ему нужен RISC-V режим, а не ARM. Переключается
  утилитой или кнопкой на модуле, состояние видно по светодиоду.
- **`CFG_DEBUG_EN`.** По умолчанию 1, но проверить в LinkUtility — вдруг
  сброшен. Если сброшен, вернуть можно только через ISP, то есть сначала
  шаг 1.
- **PB14 (TIO) и PB15 (TCK).** В прошивке не используются, но проверить,
  что к ним ничего не припаяно и они не нагружены.
- **Провода.** Двухпроводной интерфейс CH58x чувствителен к длине,
  10 см уже много.
- **Питание и земля.** Общая земля между платой и WCH-Link обязательна.
  Проверить, не пытается ли LinkUtility питать плату параллельно
  аккумулятору.
- **Мотор.** Пробовать с физически отключённым мотором: броски тока при
  пуске срывают сессию отладки.
- **Версия прошивки самого WCH-Link.** Обновляется из LinkUtility.

### Шаг 4. Подумать про железо

Раз аккумулятор подключён постоянно, стоит добавить **выключатель питания
или хотя бы перемычку**. Это снимает проблему A навсегда и сильно облегчает
отладку: подача питания даёт RPOR, при котором пин BOOT читается штатно.

## 5. Что известно про сам загрузчик

| | |
|---|---|
| Адрес | `0x00078000`, 24 КБ (`BOOT_LOAD_ADDR` в `CH583SFR.h`) |
| Разрешён | `CFG_BOOT_EN`, по умолчанию 1 |
| Интерфейсы | USB и UART |
| Утилита | WCHISPTool |
| Признак «сейчас в загрузчике» | `R8_GLOB_CFG_INFO & RB_BOOT_LOADER` |

USB-разъём на плате есть, но **линии данных D+/D− к чипу могут быть не
разведены** — по схеме `WeAct-CH57xCH58xCoreBoard_V10_SchDoc.pdf` цепи на
выводах 12/13 названы `PB11`/`PB10`, а на разъёме `DP1`/`DN1`, то есть
разные цепи. **Прозвонить тестером.** Если USB только питание, ISP пойдёт
только по UART — а это PA8/PA9, где у нас висит отладочный вывод.

## 7. Проблема C: самопроизвольные сбросы RPOR

**Симптом.** При частых пусках мотора чип молча перезагружается. В UART
`reset: RPOR`, никакого сигнала перед этим не звучит.

### Что исключено и чем

Каждая ветка сброса оставляет свой след, и ни одного из них в логе нет.

| Ветка | Улика | В логе |
|---|---|---|
| Кнопка → `reboot_as_power_on()` | печатает `reboot` и ждёт опустошения FIFO | нет |
| Уход в сон → `LowPower_Shutdown()` | печатает `shutdown`, пробуждение даёт `GRWSM` | нет |
| NMI детектора просадки | делает `RB_SOFTWARE_RESET` → следующий старт `SW` | нет |
| Сторожевой таймер | `WDOG` | нет |

Остаётся `RPOR` — настоящая подача питания либо срабатывание LVR.

### Почему это не LVR

Замер провала питания на старте мотора: 3.68 → **3.19 В**, глубокая часть
около 5 мс. Разбор в [HARDWARE.md](HARDWARE.md).

LVR имеет максимальный порог 2.3 В, детектор просадки стоит на 2.5 В. Провал
до 3.19 В далеко выше обоих. Чтобы дотянуться до LVR, банка должна упасть
примерно до 2.5 В — это не просадка, а обвал, и осциллограф его не видит.

Вдобавок детектор на 2.5 В обязан сработать раньше LVR и дать `SW`. Он не
срабатывает.

**Вывод: недостатком напряжения это не объясняется.**

### Что на поведение влияет

Определено перебором, механизм не установлен.

| Конфигурация | Результат |
|---|---|
| `DCDC_ENABLE = TRUE` | сбросы частые |
| `DCDC_ENABLE = FALSE`, `HAL_SLEEP = TRUE` | реже, но есть |
| оба `FALSE` | не воспроизводится |

Позже включён `CFG_RESET_EN` и вывод RST# подтянут к 3.3 В — субъективно
стало ещё лучше. **Механизм неясен:** пока `CFG_RESET_EN = 0`, PB23 остаётся
обычным GPIO и сбросить чип через него нечем. Возможные объяснения — вместе
с галкой перезаписался весь конфигурационный байт, либо совпадение с
перепрошивкой. Не проверено.

### Статус

**Не объяснено.** Опубликованной errata на CH582F найти не удалось. Рабочая
версия — особенность кремния в тракте DC-DC и низкого потребления при быстром
фронте на питании. Не доказана.

### Если вернётся

- Слушать сигнал: `buzzer_critical()`, три низких 250 Гц, играет при старте
  на любой `RPOR`. UART для этого не нужен, см. README.
- Сброс по выводу RST# рапортуется кодом `RST#`, а не `RPOR`, так что нажатие
  кнопки с этим не спутать.
- Цена обходного пути мала: DC-DC выключен — ток контроллера на фоне мотора
  0.7 А не виден, а в глубоком сне DC-DC отключается принудительно, замеренные
  0.8 мкА не изменились. `HAL_SLEEP = FALSE` стоит тока только пока устройство
  рекламируется.
- Если возвращать `HAL_SLEEP`, целиться в момент, а не в сам сон: запретить
  засыпание ещё пару сотен миллисекунд после остановки мотора в
  `App_SleepAllowed()` — шина в это время ещё восстанавливается.

## 8. Главное в двух строках

Проблема A, скорее всего, уже решена в коде: `R16_INT32K_TUNE = 0xFFFF`
перед `RB_SOFTWARE_RESET` даёт сброс **типа power-on**, при котором ПЗУ
опрашивает пин BOOT. Приём из самого SDK WCH, не с форума. Проверка —
строка `reset: POR` в UART. Запасной вариант остался прежним: галка
`CFG_RESET_EN` в WCH-LinkUtility — на этой плате она уже поставлена, и
штатный вход в ISP работает: зажать K2, нажать K1.

Проблема B в прошивке не лежит: выключение сторожевого таймера, сна и
детектора просадки ничего не изменило. Копать инструмент и монтаж.

Проблема C обойдена выключением DC-DC и автосна стека, но не объяснена.
